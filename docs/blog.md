## 正文

### 开头：三个让人不放心的地方

网上六爻排盘工具很多，用起来总有三件事让人不放心：

1. **摇卦的随机看不见**。你点了「摇一摇」，鬼知道它是真随机、还是 `Math.random` 甚至写死的数组。
2. **盘面会变**。同一卦换个工具、换个模型问一遍，纳甲、世应、六亲居然能不一样。
3. **结论被当成承诺**。「必成」「必败」这种话直接印在盘面上，出了事没人负责。

我做的这个工具（**野鹤六爻**）就是围绕这三点反向设计：**随机必须可核查、盘面必须确定、结论必须分層**。

---

### 一、随机：为什么必须是 Web Crypto

六爻的三钱法有严格概率：三枚铜钱，字面记 2、背面记 3，六次投掷，和为 6/7/8/9。

- 6 老阴（三字）、7 少阳（一背）、8 少阴（两背）、9 老阳（三背）
- 概率分别是 **1/8 · 3/8 · 3/8 · 1/8**

所以「摇卦」这件事根本不能凑：它不是抽一个 6~9 的随机数，而是**真的掷三枚币**，再把三面相加。这个项目里每次投掷都来自 `crypto.getRandomValues`，而且是逐位取 `Uint32` 的最低有效位——2³² 能整除 2，天然没有取模偏差。

两个细节：

- **缺 Web Crypto 就直接报错**，绝不静默回落 `Math.random`。宁可用不了，也不给你一个假随机。
- 有一条测试专门扫源码：起卦路径上出现 `Math.random` 就挂 CI；另有一条跑大样本卡方检验。50 万掷的实测是 6:0.1255 / 7:0.3746 / 8:0.3753 / 9:0.1246。

顺手说个只有真做才会遇到的坑：**8 少阴是「背背字」**。三枚币面里两背一字，显示的时候如果按「先字后背」拼，方向就反了。这种细节错了，概率还是对的，但老手一眼看出不对。

### 二、盘面：算出来的东西，不许模型插手

排盘这一层是完全确定性的：输入是「六个爻值 + 起卦时刻」，输出是纳甲装卦的整张卦单。

- 纳甲装卦、安世应、定六亲、旬空、伏神、六神、月卦身
- 十三项实用神煞：贵人、禄神、羊刃、文昌、驿马、桃花、将星、华盖、谋星、劫煞、灾煞、天医、天喜

为了让这层可信，引擎做了差分测试：**4696 个卦案逐案比对，SHA-256 指纹全一致**。换句话说，同一卦在哪儿排，结果都该一模一样——如果不一样，那是 bug，不是「流派不同」。

另一个刻意的选择：**盘面上不标用神、不印吉凶判词**。

很多工具会在盘面旁边直接写「用神：妻财丑土」「断：凶」。问题是，盘面是事实，断语是判断，两者混在一张纸上，用户很容易把判断当成事实。所以这里盘面只呈现确定性排盘，判断全部下沉到解卦正文里，并且明确标注那是模型的解读。

---

### 三、解读：只发事实，四段，而且 key 是你自己的

点「解卦」时，发给服务端的**只有盘面事实**：卦名、纳甲、六亲、世应、动变、伏神、旬空、神煞、卦爻辞，加上你写的问句。没有用神结论，没有预设判断。

服务端拼 prompt（不随前端下发），流式返回四段：

> **取用 / 盘面 / 走势 / 应期**

四段是硬约束，不是让模型自由发挥：先说取哪一爻为用、为什么；再说盘面上哪些事实支持这个取法；然后讲走势；最后给应期的时间线索。字数也有上限（400–550，硬上限 600），逼它说人话。

关于大模型，这里做了一个可能有点反直觉的决定：**不内置 key，用户自带**。

- 配置只存在你自己浏览器的 `localStorage`，不上传、不入库；
- 解卦时随请求发一次，服务端只做转发，不落库、不写日志；
- 支持任何「OpenAI 兼容」接口：DeepSeek、OpenAI、Moonshot、智谱、通义、OpenRouter、SiliconFlow、本地 Ollama，甚至自建网关。

代价是用户要自己准备一个 key；好处是**没有中间商，也没有「本站已为你充值」这种暧昧**。

当然，一个公开的转发接口需要防滥用，所以服务端有三层：

- **同源校验**：带了 `Origin` 但不是本站的请求直接 403（挡住别人拿你的站当免费代理）
- **双窗限流**：8 次/分 + 60 次/时（每 IP）
- **上游白名单**：只允许名单内的供应商域名，且拦截内网地址（防 SSRF）

### 四、案例：把《增删卜易》的卦例搬进来，还能一键还原盘面

只讲工具不讲案例，容易空。所以内置了《增删卜易》卦例 100 例（据朱辰彬《增删卜易卦例初探》整理文本抽取），每例保留：古筮知识、占问、干支旬空、本卦变卦、原注、用神 / 吉凶 / 应期三段评述。

有意思的是「**一键排出此卦**」怎么做的：

1. 原文只给卦名（比如「乾之小畜」），先从卦名反推六爻二进制，再反推六次投掷值（同位阴阳相异就是动爻，映射成 6/7/8/9）；
2. 原文只给「辰月戊申日」，没有公历年。那就**在 1990–2026 里找同月建、同日辰的一天**作为对应公历。

这样点开看到的盘面，月建、日辰、旬空、世应、动爻和原书完全对得上——不是「大概像」，是逐例核对过。

顺带说，原文的空格和折行早就乱了（有一例甚至把六行卦象挤成一行），所以卦盘不是照抄文本，而是用同一套引擎重排。**能重排的前提，是排盘真的确定性。**

### 五、界面：宣纸、朱砂，和手机上够得着的按钮

视觉上没走「赛博玄学」那套霓虹，就是宣纸底、松墨绿、朱砂点缀。站名用毛笔楷书（按四个字做了子集，2.7KB），六爻盘面按古法卦单的定宽栅格排，字号和列宽都不改，只在窄屏整体等比缩放——不重排版式，只改尺寸。

移动端做了两件小事：

- 「掷钱起爻」固定在底部悬浮条里，单手够得到；
- 支持装成 PWA：加到主屏后全屏无地址栏，**起卦和排盘离线可用**（这两步全在本地算），解卦才需要联网。

### 六、工程：Cloudflare Workers + D1，部署文档就在 README

线上是 Cloudflare Workers（vinext / workerd）+ D1：

- 全站计算在浏览器，Worker 只做静态资源、解卦转发、卦例读写；
- 部署产物 1.5MB / gzip 487KB，免费额度足够；
- 历史排盘存在 D1，按匿名设备 Cookie 隔离，只存起卦输入，打开时用引擎重排同一卦。

我在仓库 README 里写了完整的部署步骤：登录、建 D1、绑自定义域名（**用 Custom Domain，不要用路由，否则没有 DNS 记录**）、验收清单、边缘限流规则、回滚方式，还有一张「常见坑」表——比如 `public/` 下的文件名带 `@` 会被 Workers Assets 编码成 `%40` 然后 307 循环，本地 dev 完全看不出来，手机 DPR 3 直接裂图。

### 七、边界：这不是一个「预测保证」工具

必须说清楚：

- 盘面是算出来的，解读是模型基于盘面事实给的**参考**；
- 不承诺准确率，也不把「或然」说成「必然」；
- 涉及健康、法律、财务，请以医生、律师、专业人士的意见为准。

工具的价值在于：**把可计算的部分算准、算稳，把不可计算的部分讲清楚它是判断**。这也是我砍掉很多东西的原因——不做用神规则的自动推断、不做应期的自动排定、盘面上不印吉凶。
